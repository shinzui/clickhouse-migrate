Migrating Replicated ClickHouse

Production ClickHouse deployments often keep two or more live copies of every table. clickhouse-migrate currently supports one directly addressed server. This page explains what replication changes, where the tool stops today, and how we plan to support replicated clusters safely.

Written for contributors and users who have not worked with ClickHouse. It summarizes ExecPlan 12, which has the full detail.

Planned work, not yet released

Everything below describes a design. Until a release says otherwise, the supported setup is still the one in the compatibility guide: one directly addressed server, ordinary databases, and the exact server versions listed there. Replicated tables, load balancers and cluster endpoints are refused.

ClickHouse in two minutes

ClickHouse is a database built for analytics: it stores huge numbers of rows and answers questions like "how many page views per day last month" quickly. Like most databases, a ClickHouse server holds databases, and each database holds tables.

Each table declares an engine, which decides how its rows are stored on disk. Nearly every real table uses an engine from the MergeTree family. Variants such as ReplacingMergeTree and AggregatingMergeTree add behaviour like collapsing duplicate rows. Databases have engines too; an ordinary one is Atomic.

A production setup usually avoids depending on one machine, so it runs several replicas: servers that each hold a full copy of the data. To keep them in step, ClickHouse uses a small coordination service called Keeper, which keeps a shared log of every change. Clients often reach the cluster through one network address, such as a load balancer or a managed service's endpoint, that may route each new connection to any replica.

Rows are only copied between replicas for tables whose engine says so: ReplicatedMergeTree instead of MergeTree, ReplicatedReplacingMergeTree instead of ReplacingMergeTree, and so on. Clusters are commonly set up so that every database is a Replicated database. With the setting database_replicated_allow_only_replicated_engine, a login is made to refuse any table that would not be copied, failing with error code 56. That setting is the reason this design exists.

What clickhouse-migrate does

A migration is a numbered SQL change, such as "create the events table" or "add a column". clickhouse-migrate applies pending migrations in order and remembers what it has done in a ledger: an append-only table in the database that records every step. Before anything runs, it does four safety checks.

The envelope is a check on each statement's text that only allows familiar kinds of SQL. Each step also gets a checksum, a fingerprint used to detect a migration that was edited after it ran. On every new connection, an admission probe asks the server who it is and which version it runs, and refuses anything unexpected. Every request also carries a fixed set of settings, called the completion policy, which decides when the server may say "done".

Each of those checks was written for a single server. Figure 2 shows where each one stops a replicated cluster.

The changes, one at a time

Single-server targets keep working exactly as they do now: same requests, same checksums, same ledger. Everything below applies only when a target is configured as a replicated cluster.

Keep the version list current

The tool accepts only exact server versions it has tested, because a new release can change behaviour the safety checks rely on. Managed ClickHouse services upgrade patch releases on their own schedule, so a server that worked yesterday can be refused today. As a first, separate step, the plan qualifies Altinity's 26.3.60.10002.altinitystable build with the full existing test suite and adds it to the list. Replicated support is then tested on that build.

Trust a set of replicas, not one server

Every ClickHouse server has a permanent ID, which ClickHouse calls its server UUID. Today you configure the one ID you expect, and the tool checks it on every new connection so a request can never land on the wrong machine. Behind a load-balanced address, a second connection can land on another replica, which has a different ID and would be refused.

A replicated target will instead name the cluster and the exact set of replica IDs. Each connection is accepted if its ID is in the set. At the start of each run, the tool also asks the cluster which replicas it has and refuses to continue unless that list matches the configured set exactly.

Say "done" only when every replica has the change

When the tool records a step in the ledger, it must be certain the record survives. With one server, "the server said OK" is enough. With two replicas, the replica that received the write can say OK and then fail before it has passed the row to the other one. The acknowledged record would then be gone.

Replicated targets will ask ClickHouse to wait for all of them. An insert quorum equal to the number of replicas makes an insert succeed only after every replica stores it. alter_sync=2 and mutations_sync=2 make schema changes wait for every replica, and reads use sequential consistency so a replica that is behind refuses to answer instead of returning stale data. If a replica is down, migrations stop instead of running half-way.

Give replicated targets their own fingerprint

A migration's checksum covers its exact SQL, its names, and the completion policy. That policy is included on purpose: running the same SQL with different "when is it done" rules is a different operation, and the ledger should not treat the two as the same. Waiting for every replica is such a change, so replicated targets get a new policy and a new checksum format, sha256-v2. The existing sha256-v1 format and every published test vector stay byte-for-byte the same, so existing ledgers remain valid.

Allow replicated table engines in migration SQL

The envelope check is deliberately narrow and works on the text of each statement. It will start accepting the six Replicated…MergeTree engine names, but only where an engine name belongs. It will keep rejecting SQL that tries to manage replication by hand, which a Replicated database already does. Migrations that create databases are refused on replicated targets: the cluster operator creates those databases ahead of time on every replica.

Statement fragmentPlanned resultWhy
ENGINE = ReplicatedMergeTree ORDER BY idacceptedThe normal way to create a copied table.
ENGINE = ReplicatedReplacingMergeTree(updated_at)acceptedOrdinary engine arguments are fine.
ReplicatedMergeTree('/clickhouse/tables/x', 'r1')rejectedAn explicit Keeper path. The server fills in the right one and refuses paths that differ.
… ON CLUSTER my_clusterrejectedA Replicated database already sends table changes to every replica.
CREATE DATABASE analytics ENGINE = Replicated(…)rejectedDatabases are created by the cluster operator, not by migrations.
ENGINE = Distributed(…)rejectedSpreading data across shards is out of scope.
ENGINE = MergeTree inside a Replicated databasepasses the checkA login restricted to replicated tables makes the server refuse it with error code 56. The run fails loudly before anything is half-applied.

Keep the ledger on replicated storage

The ledger is a table too, so the same rules apply to it. On a replicated target it lives in a Replicated database that already exists and uses a ReplicatedMergeTree table. The tool checks the table's exact layout as reported by ClickHouse, as it does today.

LedgerSingle server (unchanged)Replicated cluster (planned)
DatabaseCreated by the tool as AtomicMust already exist as Replicated; the tool never creates it
Table engineMergeTreeReplicatedMergeTree, no Keeper arguments
Appending an entryDone when the server stores itDone when every replica stores it

Checksum format recordedsha256-v1sha256-v2

Order of work

The first step ships by itself. The second is an experiment whose measurements fix the exact settings and expected text the later steps rely on.

  1. Qualify Altinity 26.3.60.10002 ships firstRun the full test suite against the new build, add it to the list of accepted versions, and release a patch version.
  2. Build a two-replica test cluster and measure prototypeStart two ClickHouse servers and Keeper in local containers and record how ClickHouse really behaves: the exact engine text it reports, which settings make writes wait, what a stopped replica does, and the error-56 refusal. If no setting makes acknowledged writes wait for every replica, we stop and rethink.
  3. Replicated targets and admissionConfigure a cluster name and replica set, admit each connection against the set, and check cluster membership at the start of each run.
  4. New completion policy and sha256-v2Replicated targets get their own fingerprints. Every existing checksum and ledger test must pass unchanged.
  5. Replicated engines in the SQL checkAccept the six engine names where an engine belongs; keep rejecting manual replication; refuse database creation on replicated targets.
  6. Replicated ledgerInitialize, append and read in a pre-existing Replicated database, and survive each replica restarting in turn.
  7. End-to-end test, docs, releaseA new just test-replicated run applies an example migration set through an address that alternates between replicas. Then the supported setup is documented in a new design record and the library is released.

What this means for you

clickhouse-migrate will not rewrite anyone's SQL. Quietly turning MergeTree into ReplicatedMergeTree at run time would mean the ledger records SQL that never ran, and the checksum could no longer prove which SQL ran. Migration authors write the replicated engines themselves.

Migration authors

Write Replicated…MergeTree engines without Keeper path arguments, leave out ON CLUSTER, and do not create databases. A project that also supports single servers keeps separate migration sets for the two kinds of target.

Cluster operators

Create the application and ledger databases as Replicated on every replica before the first run. Give the migration login the replica set's server UUIDs and cluster name. A replicated target starts a fresh ledger; existing single-server ledgers are not converted.

Still out of scope

Multiple shards, Distributed tables, ON CLUSTER DDL, automatic SQL rewriting, and any server version that has not been tested. Evidence from local test clusters does not certify a particular managed service.

Terms used on this page

Replica
One ClickHouse server holding a full copy of the data. Production clusters commonly run two or three.
Keeper
ClickHouse's coordination service. It keeps the shared log that tells replicas which changes and data they must apply.
Engine
The storage method a table or database declares. ReplicatedMergeTree tables copy their rows to every replica; MergeTree tables do not.
Replicated database
A database whose table definitions are kept identical on every replica through Keeper. It does not copy rows by itself.
Error code 56
ClickHouse's refusal to create a non-copied table inside a Replicated database when database_replicated_allow_only_replicated_engine is on for the login.
Ledger
clickhouse-migrate's append-only record of every migration step, stored in the database it manages.
Envelope
A text-level check that only lets known, reviewable kinds of SQL into a migration.
Checksum
A fingerprint of a migration that detects edits after it ran.
Admission probe
A query sent on every new connection to confirm the server's ID, version and settings before any real work.
Completion policy
The settings sent with every request that define when the server may report "done".
Insert quorum
A setting that makes an insert succeed only after a given number of replicas store it.
Sequential consistency
A read setting that refuses to answer from a replica that has not caught up.
